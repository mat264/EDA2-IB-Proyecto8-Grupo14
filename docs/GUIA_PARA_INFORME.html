Párrafo Base Listo para el Informe

Resumen— El crecimiento de los catálogos digitales de entretenimiento dificulta que los usuarios encuentren contenido relevante de manera rápida. En este trabajo se presenta el diseño, implementación y evaluación de un sistema de recomendación colaborativa de películas desarrollado en Java 17 y JavaFX, fundamentado en un grafo bipartito no dirigido y en el algoritmo de Búsqueda en Anchura (BFS). El modelo divide los nodos en dos grupos independientes: usuarios y películas, conectados únicamente cuando un usuario califica una película con una puntuación igual o superior a 4.0 sobre 5.0. A partir de un usuario objetivo, el algoritmo explora tres niveles de profundidad: las películas que el usuario ya vio (Nivel 1), otros usuarios con gustos similares que vieron esas mismas películas (Nivel 2) y nuevas películas candidatas vistas por dichos usuarios similares (Nivel 3). La implementación utiliza listas de adyacencia basadas en tablas hash (HashMap y HashSet), logrando verificaciones de películas ya vistas en tiempo constante O(1). Finalmente, el sistema incorpora un módulo de evaluación experimental con división 80/20 (entrenamiento/prueba) que mide la precisión (Precision@K), la exhaustividad (Recall@K), el tiempo de respuesta en milisegundos y el consumo de memoria RAM.

Palabras clave— Grafo bipartito, búsqueda en anchura (BFS), sistemas de recomendación, tablas hash, similitud de Jaccard, JavaFX.

I. INTRODUCCIÓN
Los sistemas de recomendación colaborativa permiten sugerir contenidos a un usuario aprovechando el historial de una comunidad con intereses afines [1]. En el ámbito cinematográfico, cuando dos personas califican positivamente las mismas películas, existe una alta probabilidad de que otros títulos vistos por una de ellas resulten atractivos para la otra. Esta relación entre personas y catálogo puede modelarse de forma natural mediante un grafo bipartito, donde los nodos se dividen en dos grupos separados (Usuarios y Películas) y cada conexión representa una calificación favorable igual o mayor a 4.0 [2].

El objetivo de este proyecto es desarrollar un sistema de recomendación explicable y portable en Java 17 y JavaFX que recorra dicho grafo bipartito mediante Búsqueda en Anchura (BFS) hasta tres niveles de distancia. A diferencia de los sistemas que ocultan el motivo de sus sugerencias, nuestra implementación detalla qué películas vistas y qué usuarios similares originaron cada recomendación. Como limitación natural de los métodos colaborativos basados en grafos, se identifica el escenario de arranque en frío (cold-start): cuando un usuario aún no registra calificaciones positivas, no existen conexiones iniciales para expandir la búsqueda, caso que el software gestiona de forma segura devolviendo una lista vacía.

3. Sección II del Informe: Marco Teórico

¿Qué debes explicar aquí?

Explica los 4 conceptos fundamentales usando el ejemplo real de nuestro programa:

  1. Grafo Bipartito: Tiene dos columnas de nodos: a la izquierda Usuarios y a la derecha Películas. Solo se conectan Usuarios con Películas, nunca usuarios entre sí.
  2. Listas de Adyacencia en HashMap y HashSet: Guardan para cada usuario solo las películas que vio, permitiendo consultas instantáneas en tiempo O(1) (sin recorrer listas largas).
  3. Búsqueda en Anchura (BFS) en 3 Saltos: Avanza capa por capa desde el usuario elegido hasta descubrir películas nuevas a 3 pasos de distancia.
  4. Similitud de Jaccard: Un número entre 0.0 y 1.0 que mide qué tan parecidos son dos usuarios dividiendo las películas que tienen en común entre el total de películas entre ambos.
Ejemplo Práctico con Nuestro Dataset Demo (Úsalo en el Informe y en la Defensa) Supongamos que elegimos al Usuario U1:
  • Salto 1 (Películas Vistas): El sistema ve que U1 calificó bien a The Matrix, Inception e Interstellar.
  • Salto 2 (Usuarios Similares): El sistema busca quién más vio esas películas y encuentra que el Usuario U2 y el Usuario U4 también vieron The Matrix e Inception (tienen una similitud de Jaccard de 0.40 con U1).
  • Salto 3 (Películas Candidatas): El sistema revisa qué otras películas vieron U2 y U4 que U1 todavía no haya visto, encontrando The Dark Knight y Blade Runner 2049.

II. MARCO TEÓRICO
Un grafo bipartito no dirigido está formado por dos conjuntos independientes de nodos —Usuarios y Películas— donde cada arista une a un usuario con una película que calificó positivamente [1]. Dado que en un catálogo real cada persona solo ha visto una pequeña parte de las películas disponibles (grafo disperso), la estructura se implementa mediante listas de adyacencia sobre tablas hash (HashMap y HashSet) [2]. Sobre esta representación se aplica el algoritmo de Búsqueda en Anchura (BFS) en tres saltos: el Nivel 1 recupera las películas vistas por el usuario objetivo; el Nivel 2 identifica a los usuarios similares que coincidieron en esas películas; y el Nivel 3 recolecta las películas candidatas vistas por dichos vecinos que el usuario objetivo aún no conoce. Finalmente, para ordenar las sugerencias se combina la cantidad de caminos encontrados con el coeficiente de similitud de Jaccard, que mide la proporción de gustos en común entre dos usuarios en una escala de 0.0 a 1.0.

III. ANÁLISIS Y DISEÑO
El sistema se estructuró bajo el patrón de separación por capas en cinco paquetes dentro de un proyecto Apache Maven portable. El núcleo de datos reside en la clase BipartiteGraph (paquete model), la cual mantiene dos tablas hash sincronizadas: userToMovies, que relaciona cada identificador de usuario con su conjunto HashSet de películas vistas, y movieToUsers, que registra qué usuarios calificaron cada película con nota igual o mayor a 4.0. La clase CsvDatasetLoader (paquete util) garantiza que el programa funcione en cualquier sistema operativo leyendo los datos embebidos mediante flujos de recursos. Por su parte, BFSRecommender (paquete algorithm) ejecuta la búsqueda por niveles y genera explicaciones trazables, mientras que Evaluator (paquete metrics) automatiza las pruebas de rendimiento que se visualizan en las dos pestañas de la interfaz gráfica JavaFX (paquete ui).

5. Sección IV del Informe: Implementación

¿Qué debes escribir aquí?

Explica cómo funciona por dentro el método recommendTopK de la clase BFSRecommender.java y cómo se calcula el puntaje de cada película recomendada. Puedes incluir este pseudocódigo limpio en el informe: 

PROCEDIMIENTO RecomendarTopK(GrafoBipartito grafo, Entero idUsuario, Entero K):
    1. peliculasVistas = grafo.obtenerPeliculasDeUsuario(idUsuario)   // Nivel 1 (HashSet O(1))
    2. SI peliculasVistas está vacío ENTONCES RETORNAR lista vacía    // Control Cold-Start

    3. PARA CADA peliculaVista EN peliculasVistas HACER:              // Nivel 2 (Usuarios Similares)
           usuariosQueLaVieron = grafo.obtenerUsuariosDePelicula(peliculaVista)
           Guardar qué películas en común tiene cada usuarioSimilar con idUsuario

    4. PARA CADA usuarioSimilar descubierto HACER:
           Calcular similitudJaccard entre idUsuario y usuarioSimilar

    5. PARA CADA usuarioSimilar HACER:                                // Nivel 3 (Películas Candidatas)
           PARA CADA peliculaCandidata vista por usuarioSimilar HACER:
               SI peliculasVistas contiene peliculaCandidata ENTONCES:
                   DESCARTAR (búsqueda instantánea O(1) en HashSet)
               SINO:
                   caminos = cantidad de películas en común con ese usuarioSimilar
                   puntaje[peliculaCandidata] += caminos * (1.0 + similitudJaccard)
                   Guardar explicación (películas puente y usuarioSimilar)

    6. Ordenar las películas candidatas de mayor a menor puntaje
    7. RETORNAR las primeras K películas de la lista ordenada
Nota para la Defensa Oral: ¿Por qué nunca se recomiendan películas que el usuario ya vio? Si en la defensa te preguntan cómo evitamos recomendar una película repetida sin volver lento el programa, responde:
"Al empezar el recorrido en el Nivel 1, guardamos las películas vistas por el usuario en un HashSet. Luego, en el Nivel 3, usamos level1WatchedByU.contains(peliculaCandidata), que verifica en tiempo constante O(1) (de forma instantánea gracias a la tabla hash) si el usuario ya la vio y la descarta de inmediato."

6. Sección V del Informe: Complejidad Big-O y Relación con NP-Completos

Parte A: Por qué usamos Listas de Adyacencia y Tabla Big-O

Explica primero por qué elegimos Listas de Adyacencia con HashMap y HashSet en lugar de una Matriz de Adyacencia: en un catálogo real con miles de películas, cada usuario solo ha visto unas pocas. Una matriz de Usuarios por Películas desperdiciaría memoria llenándose de ceros (O(U * V)), mientras que nuestras listas en HashMap solo guardan las calificaciones que sí existen (O(U + V + E)).

Operación del Programa Método en Java Complejidad de Tiempo Complejidad de Memoria ¿Qué significa en la práctica?
Insertar una calificación addInteraction O(1) O(1) Agrega la conexión al instante en los dos mapas hash.
Construir todo el grafo buildFromDataset O(V + R) O(U + V + E) Lee una sola vez las V películas y las R filas del archivo CSV.
Verificar si ya vio una película hasUserWatchedMovie O(1) O(1) Búsqueda instantánea en HashSet sin recorrer listas.
Paso 1 BFS (Usuario Objetivo) recommendTopK O(1) O(1) Encuentra al usuario directamente por su ID en el HashMap.
Paso 2 BFS (Películas Vistas) recommendTopK O(V_u) O(V_u) Solo recorre las V_u películas que vio ese usuario.
Paso 3 BFS (Usuarios Similares) recommendTopK O(V_u * U_p) O(K_vecinos) Por cada película vista, revisa los U_p usuarios que también la vieron.
Paso 4 BFS (Candidatas y Top-K) recommendTopK O(K_vecinos * D + C log C) O(C) Revisa las D películas de cada vecino y ordena las C películas candidatas.

Parte B: Relación con Problemas NP-Completos (Requisito Teórico de la Guía)

Cómo explicar la diferencia entre nuestro algoritmo (Clase P) y los problemas NP-Completos
  • ¿Por qué nuestro recomendador BFS está en la Clase P (Polinómico)? Porque para recomendar películas a un usuario solo damos 3 saltos sobre sus vecinos inmediatos y ordenamos las películas candidatas. El tiempo crece de forma moderada y el computador lo resuelve en menos de un milisegundo.
  • ¿Qué problema sobre este mismo grafo bipartito SÍ es NP-Completo? El problema de Cobertura Mínima de Catálogo (Minimum Set Cover): "¿Cuál es el grupo más pequeño posible de K películas que debemos comprar para asegurar que el 100% de los usuarios del sistema tenga al menos una película que le guste?". Otro ejemplo es encontrar la Comunidad Completa Máxima (Maximum Edge Biclique).
  • ¿Qué significa Verificación en P (Clase NP)? Si alguien nos entrega una lista de K películas y asegura que cubren a todos los usuarios, comprobarlo es muy rápido (Clase P): solo miramos en el HashMap qué usuarios vieron esas K películas. Pero encontrar esa lista mínima desde cero obliga a probar millones de combinaciones posibles (NP-Completo).
  • ¿Qué son las Reducciones Polinómicas y los Gadgets? Para demostrar que un problema en nuestro grafo bipartito es NP-Completo, se toma un problema difícil ya conocido (como 3-SAT) y se traduce a nodos de usuarios y películas artificiales llamados gadgets (pequeñas piezas de grafo que imitan decisiones de verdadero o falso).

V. ANÁLISIS DE COMPLEJIDAD Y RELACIÓN CON NP-COMPLETITUD
El algoritmo de recomendación BFS de tres niveles implementado en este proyecto pertenece a la clase de complejidad P (Tiempo Polinómico) [1], ya que para un usuario con V_u películas vistas y K_vecinos usuarios similares realiza un recorrido local acotado por O(V_u * U_p + K_vecinos * D + C log C), apoyado en consultas instantáneas O(1) sobre tablas hash. Sin embargo, cuando se plantean problemas de optimización global sobre este mismo grafo bipartito Usuario-Película, surgen problemas clásicos NP-Completos como la Cobertura Mínima de Catálogo (Minimum Set Cover) —determinar el menor subconjunto de películas capaz de cubrir a todos los usuarios activos— o el problema de la Comunidad Bipartita Completa Máxima (Maximum Edge Biclique) [1]. Estos problemas pertenecen a la clase NP porque admiten verificación en tiempo polinómico (P): dada una solución candidata de k películas, es posible verificar rápidamente en el HashMap si la unión de sus espectadores cubre a todos los usuarios. No obstante, encontrar dicho subconjunto óptimo requiere explorar un espacio combinatorio exponencial, cuya dificultad se demuestra formalmente mediante reducciones polinómicas que emplean subestructuras de nodos y aristas llamadas gadgets.

VII. CONCLUSIONES Y RECOMENDACIONES
1. El modelado del sistema de recomendación sobre un grafo bipartito implementado con tablas hash (HashMap y HashSet) permitió alcanzar tiempos de construcción y de recomendación inferiores a un milisegundo por usuario, ahorrando memoria frente a una representación matricial.
2. El recorrido en anchura (BFS) en tres saltos combinado con la similitud de Jaccard demostró ofrecer recomendaciones precisas y 100% trazables, permitiendo al usuario conocer exactamente qué películas vistas y qué vecinos similares justifican cada sugerencia.
3. El uso de un conjunto HashSet para registrar el historial del usuario en el Nivel 1 permitió descartar películas ya vistas en tiempo constante O(1) durante la exploración del Nivel 3.
4. Se recomienda como mejora futura incorporar nodos de géneros cinematográficos al grafo bipartito para mitigar el problema de arranque en frío (cold-start) cuando ingresan usuarios nuevos sin calificaciones previas.
